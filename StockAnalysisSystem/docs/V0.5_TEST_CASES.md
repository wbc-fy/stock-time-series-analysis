# V0.5 Flink 端到端验收

在 `StockAnalysisSystem` 目录执行。需要已启动的 Kafka/Flink Compose 栈、已创建的 V0.5 topics、一个运行中的 `stock-daily-indicator-v1` 作业，以及包含 `confluent-kafka`、`simplejson` 的 Python 环境。脚本会通过 Flink REST API 自动发现唯一运行中的作业；也可传 `--job-id`、`--flink-url`、`--bootstrap-servers` 和各 topic 参数。所有场景有界等待（默认 180 秒），不匹配时退出码为 1。输出只统计本次 UUID 派生的股票代码；每个消费者使用新的 group ID 和 `read_committed`。

## 自动验收步骤

```powershell
D:\Python\python.exe -m pytest python-services\python-collector\tests\test_verify_v05_flink.py -v
D:\Python\python.exe scripts\verify_v05_flink.py --scenario valid
D:\Python\python.exe scripts\verify_v05_flink.py --scenario late
D:\Python\python.exe scripts\verify_v05_flink.py --scenario invalid
D:\Python\python.exe scripts\verify_v05_flink.py --scenario recovery-before
docker restart stock-flink-taskmanager
docker compose -f infrastructure\docker-compose.yml ps
D:\Python\python.exe scripts\verify_v05_flink.py --scenario recovery-after
```

只在 `recovery-before` 返回 `PASS` 且写出 `StockAnalysisSystem/.tmp/v05-recovery.json` 后重启 TaskManager。不要删除该清单、Kafka topics/volumes 或 Flink checkpoints，也不要 `down -v` 或取消作业。清单已存在时，`recovery-before` 会拒绝覆盖；要进行新的一轮测试，给前后两条验证命令传同一个新路径，例如 `--recovery-file .tmp/v05-recovery-review.json`。TaskManager 重启是唯一必要的扰动，`recovery-after` 会等待原 Job ID 和三个 slot 恢复。

恢复清单还保存 TaskManager 的 Docker container ID、name、Compose project/service 和 `State.StartedAt`。恢复后必须是同一预期容器/服务且 `StartedAt` 严格变新；`RestartCount` 仅记录供参考（`docker restart` 不保证该字段增加）。两阶段各自在观察到已提交结果后记录 epoch-ms 屏障，只接受 `trigger_timestamp > 屏障` 的 `COMPLETED` checkpoint。随后以新的 `read_committed` group 从各分区 low watermark 重读本次唯一股票，经过 25 秒提交后静默窗口仍必须恰好得到预期的 10 或 20 条结果，任何迟来的重复提交都会失败。

## 验收断言

两阶段 `recovery-before/after` 仅验证 TaskManager 重启后已有提交与窗口状态延续：故障前十条已经 checkpoint 提交，不能据此证明故障发生在未提交事务期间。in-flight exactly-once 验收必须另外执行以下隔离场景。

| 场景 | 输入与期望 |
| --- | --- |
| `valid` | 两只唯一股票各 D1–D20；每条主输出的 Kafka key、完整 JSON 字段、源事件 ID、六位小数、MA5/10/20、成交量均线、量比、窗口大小和预热标志与独立 Decimal/HALF_UP 计算一致。同日 D20 覆盖产生第二条同业务 `eventId`，但窗口仍为 20；本次股票不进入 late/DLT。 |
| `late` | D1–D20 后发送更旧的 D19；late topic 恰有一条，包含原事件、最新日期和原因；此时主 topic 没有新输出。随后覆盖 D20，核对均线与窗口以证明旧事件未污染状态。 |
| `invalid` | 发送损坏 JSON 和 Kafka key/`tsCode` 不一致的有效 JSON；Flink DLT 恰有两条，`originalKey`、`originalPayload`、来源 topic/partition/offset、`JSON_PARSE` 或 `KEY_MISMATCH` 完整保留，主 topic 无输出。 |
| `recovery-before` | 提交 D1–D10，观察十条唯一已提交输出；只接受观测后触发且已完成的 checkpoint，再从头重读核对；将 Docker 身份/启动时间、观测屏障、checkpoint ID/触发时间、股票代码和十个 `eventId` 保存到清单。 |
| `recovery-after` | 先证明同一 TaskManager 的启动时间变新，再提交 D11–D20；观察结果后等待新的屏障后 checkpoint；新 `read_committed` 消费组从头重读本次股票，要求每个日期/业务 ID 恰好出现一次，全部字段、六位小数 scale 和 D20 MA20 正确，提交后静默窗口无额外输出。作业保持 `RUNNING`。 |

主输出的业务 `eventId` 是 `tsCode + tradeDate` 的确定性 ID；因此 `valid` 中的主动同日覆盖会合法地重复该 ID。恢复场景没有覆盖，任何重复的已提交 `eventId` 都是失败。

主输出每个非空十进制数值不仅要在数值上相等，其 JSON 小数刻度也必须恰好是六位；`10`、`10.0` 和 `10.0000000` 都不能替代 `10.000000`。

若某场景失败，保留脚本 JSON 输出、恢复清单、Flink Job ID 与 checkpoint 记录，先定位原因；不要为了使测试通过而清理 topics、重置消费组或更改验证标准。

## 隔离 in-flight 故障及真实 MySQL 对账

`verify_v05_isolated.py` 是会修改本地 Docker 状态的显式验收入口，必须在空闲 Session Cluster 中运行；检测到任一非终态作业时拒绝运行，避免中断现有主作业。已有主作业须由操作者先取 savepoint、取消并保留原配置；不要为了测试直接杀掉主作业。脚本只创建 UUID Topic/consumer group/deployment namespace/checkpoint 子目录，不清理数据，不复用主作业事务前缀。两个验证器均拒绝 Python `-O` / `PYTHONOPTIMIZE`，不能禁用断言后给出 PASS。

```powershell
# 空闲集群；每次选择不存在的新报告路径
D:\Python\python.exe scripts\verify_v05_isolated.py --scenario recovery --report .tmp\isolated-recovery-new.json
D:\Python\python.exe scripts\verify_v05_isolated.py --scenario real-replay --env-file '<existing-main-.env>' --report .tmp\isolated-real-replay-new.json
```

- recovery：D1–D10 已提交后取得 retained checkpoint；SIGSTOP JobManager，冻结 checkpoint coordinator；再发送 D11–D15，必须先证明五条 `read_uncommitted` 输出可见、同一批 `read_committed` 为零。在协调器仍冻结时 SIGKILL，再启动 JobManager，等待 TaskManager 自行重新注册，用同一隔离参数 `flink run -s` 显式恢复。REST restored checkpoint ID/path 必须吻合。随后发送 D16–D20，fresh `read_committed` 从 low watermark 全量重读，经过 25 秒静默窗口必须正好 20 个唯一业务键、完整字段/指标及 D20 连续状态；late/DLT 均零。不是依赖 checkpoint interval 的时序猜测。
- real-replay：只读 MySQL `000001.SZ` 的 2026-04-29..2026-05-29，先验证恰好 20 个不同实际交易日；实际调用 Collector CLI handler（`--ts-code` / 每批 7 条），再与 Decimal oracle 和既有 `FeatureEngineer.calculate_all_features` 逐日比较六指标，共 120 项（含 null）。审计全部三个输入分区：非空分区 checkpoint committed offset 必须等于 high watermark；空分区无 committed offset 不代表积压。late/DLT 必须为零。

成功时只取消本次隔离作业并保留 Topic/checkpoint。失败时保留初始资源清单和现有作业供诊断；故障证明阶段异常会在 finally 中 SIGCONT 尚冻结的 JobManager。若 SIGKILL 后失败，操作者应 `docker start stock-flink-jobmanager`，查看保留的 checkpoint metadata，再按原 namespace/topic/group 显式恢复；不要删除数据或启动同 namespace 的第二个作业。测试完成后必须用原配置及原 retained checkpoint/savepoint 恢复主作业并确认 RUNNING。

2026-10-03 实际结果：isolated recovery `v05-3bb1d81d0b53` PASS（RU=5/RC=0，chk2 恢复后20唯一）；真实 replay `v05-6b62d5764b02` PASS（20输入/20输出/120项 FeatureEngineer 对比，全部分区无积压、late/DLT0）。主部署从原 checkpoint944 显式恢复为 `d8c24038ed9e224ecc3515b0aa3996d9`，RUNNING；完整证据见 [对账报告](V0.5_RECONCILIATION_REPORT.md)。
